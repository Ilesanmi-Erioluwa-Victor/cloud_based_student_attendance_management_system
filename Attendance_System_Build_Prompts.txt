================================================================================
DESIGN AND IMPLEMENTATION OF A CLOUD-BASED STUDENT ATTENDANCE
MANAGEMENT SYSTEM (TERTIARY INSTITUTION)
STEP-BY-STEP SCAFFOLDING GUIDE & PROMPTS
(Stack: React + Tailwind CSS (frontend) | Node.js/Express (backend) |
MongoDB Atlas (database) | Brevo (transactional email) | Deployed on
Render — 100% browser-based, ZERO local installs)
================================================================================

HOW TO USE THIS FILE
--------------------------------------------------------------------------------
Each step below has:
  (a) a short explanation of what you're building, and
  (b) a ready-to-use PROMPT you can paste into an AI coding assistant
      (Claude Code, Cursor, Copilot Chat, ChatGPT, etc.) to generate that
      part of the project.

Work through the steps IN ORDER. Each prompt assumes the previous steps
already exist in your project repository, so paste them one at a time and
let the assistant finish one step before moving to the next.

Tech stack: React + Tailwind CSS (frontend) | Node.js + Express (backend,
REST API) | MongoDB Atlas via Mongoose (database) | Brevo API (attendance
alerts, welcome emails, password resets) | Render (hosting, two services:
one for the API, one for the frontend)

NOTHING is installed on your machine — no Node.js, no MongoDB, no local
package manager. Everything happens in the browser:
  - Code lives in a GitHub repository, edited via GitHub's web editor
    (github.dev) or GitHub Codespaces (full cloud dev environment with a
    terminal, opens in the browser — no download).
  - The database lives on MongoDB Atlas (cloud).
  - Emails are sent through Brevo's API (cloud).
  - The app is built and run on Render (cloud) directly from your
    repository — Render installs dependencies and starts both services
    for you.
  - Testing happens against your live Render URLs after each deploy.

STEP 0 — PREREQUISITES (do this yourself, no prompt needed, no installs)
================================================================================
1. Create a free GitHub account at https://github.com (if you don't have
   one) and create a new empty repository, e.g. "attendance-system".
2. To edit files without installing anything: either
   a. Use GitHub's built-in web editor — press "." on the repo page to
      open a full VS-Code-like editor in the browser at github.dev, or
   b. Use GitHub Codespaces (Code → Create codespace on main) — a full
      cloud VS Code environment with a terminal, still 100% in-browser.
3. Create a free MongoDB Atlas account at https://www.mongodb.com/atlas
   and create a free (M0) cluster. From there:
   - Create a database user (username + password).
   - Under Network Access, allow access from anywhere (0.0.0.0/0), since
     Render's IPs are dynamic.
   - Copy the connection string (looks like
     mongodb+srv://<user>:<password>@cluster0.xxxxx.mongodb.net/attendance_db)
     — you'll paste this into Render's dashboard later, not into any file.
4. Create a free Brevo account at https://www.brevo.com, verify a sender
   email/domain, and generate an API key under
   Settings → SMTP & API → API Keys. Keep this key ready for Render's
   dashboard too.
5. Create a free Render account at https://render.com and connect it to
   your GitHub account.

Nothing to download. Everything else happens by pasting the prompts below
into your AI assistant inside the GitHub web editor / Codespaces,
committing, pushing, and letting Render build and deploy.

STEP 3 — DATABASE MODELS (Mongoose schemas)
================================================================================
WHAT IT DOES: Defines the MongoDB collections for a tertiary-institution
attendance system — users with roles, departments, courses, enrollments,
attendance sessions, and individual attendance records.

PROMPT:
--------------------------------------------------------------------------------
Create Mongoose schemas/models for a tertiary-institution attendance
system:

1. models/User.js:
   - fields: fullName, email (unique), password (hashed), role (enum:
     'student', 'lecturer', 'admin'), matricNumber (unique, required only
     when role is 'student'), staffId (unique, required only when role is
     'lecturer'), department (ObjectId ref Department), level (e.g. 100,
     200, 300, 400 — required only for students), isActive (Boolean,
     default true), createdAt (timestamps: true).
   - Add a pre-save hook that hashes the password with bcryptjs if it was
     modified.
   - Add an instance method comparePassword(candidatePassword) using
     bcrypt.compare.

2. models/Department.js: fields: name (unique), code (unique, e.g. "CSC"),
   faculty (String).

3. models/Course.js: fields: courseCode (unique, e.g. "CSC301"),
   courseTitle, unit (Number), department (ObjectId ref Department),
   level (Number), semester (enum: 'First', 'Second'), lecturer (ObjectId
   ref User, role lecturer).

4. models/Enrollment.js: fields: student (ObjectId ref User), course
   (ObjectId ref Course), academicSession (String, e.g. "2025/2026"),
   enrolledAt (timestamps: true). Add a compound unique index on
   (student, course, academicSession) so a student cannot double-enroll
   in the same course in the same session.

5. models/AttendanceSession.js: fields: course (ObjectId ref Course),
   lecturer (ObjectId ref User), sessionCode (String, unique, short
   random code generated when a lecturer opens a session),
   date (Date, default now), startTime (Date), endTime (Date, nullable —
   session is "open" while null), isActive (Boolean, default true).

6. models/AttendanceRecord.js: fields: attendanceSession (ObjectId ref
   AttendanceSession), student (ObjectId ref User), course (ObjectId ref
   Course), markedAt (Date, default now), status (enum: 'Present',
   'Absent', default 'Present'). Add a compound unique index on
   (attendanceSession, student) so a student cannot mark attendance twice
   in the same session.

Add clear comments above each schema explaining its purpose in the system.

STEP 4 — AUTH MODULE (register, login, JWT, role-based middleware)
================================================================================
WHAT IT DOES: Lets students, lecturers, and admins register/login securely,
issues JWTs, and protects routes by role.

PROMPT:
--------------------------------------------------------------------------------
Build the authentication system for the attendance system:

1. controllers/authController.js:
   - registerUser: creates a new User (student/lecturer/admin as
     specified in the request body), validates required role-specific
     fields (matricNumber for students, staffId for lecturers), rejects
     duplicate emails/matric numbers/staff IDs with clear messages,
     hashes the password automatically via the model's pre-save hook, and
     sends a welcome email via utils/sendEmail.js (built in Step 6) after
     successful registration — do not block the response on email
     failure, just log it.
   - loginUser: verifies email + password with comparePassword(), checks
     isActive, and on success returns a signed JWT (7-day expiry,
     containing userId and role) plus basic user info (excluding
     password).
   - getMe: returns the currently authenticated user's profile from the
     JWT (via middleware).

2. middleware/authMiddleware.js: verifies the JWT from the
   Authorization: Bearer <token> header, attaches the decoded user to
   req.user, and returns 401 if missing/invalid.

3. middleware/roleMiddleware.js: exports a function authorizeRoles(...roles)
   that returns middleware rejecting the request with 403 if
   req.user.role is not in the allowed list.

4. middleware/errorMiddleware.js: a generic Express error handler that
   returns JSON { message } and never leaks stack traces or raw database
   errors in production.

5. routes/authRoutes.js: POST /api/auth/register, POST /api/auth/login,
   GET /api/auth/me (protected by authMiddleware).

Use process.env.JWT_SECRET for signing tokens — never hardcode a secret.

STEP 8 — ATTENDANCE SESSION & RECORDING MODULE
================================================================================
WHAT IT DOES: The core feature — a lecturer opens an attendance "session"
for a class period, and enrolled students mark themselves present using a
short code within a time window.

PROMPT:
--------------------------------------------------------------------------------
Build the attendance session and recording module, protected by
authMiddleware:

1. controllers/attendanceController.js + routes/attendanceRoutes.js:
   - POST /api/attendance/sessions (role: lecturer) — start a new
     AttendanceSession for a course the lecturer teaches, generating a
     short random sessionCode (e.g. 6 characters), setting startTime to
     now, and isActive true.
   - PATCH /api/attendance/sessions/:id/close (role: lecturer, own session
     only) — set endTime to now and isActive to false. After closing, for
     every enrolled student in the course who does NOT have an
     AttendanceRecord for this session, create one with status 'Absent'
     (so absentees are recorded, not just missing data).
   - POST /api/attendance/mark (role: student) — body: { sessionCode }.
     Look up the active AttendanceSession by code, verify it isActive and
     the student is enrolled in that course, then create an
     AttendanceRecord with status 'Present' for the logged-in student —
     rejecting duplicates via the unique index from Step 3 with a clear
     "already marked" message. Reject if the session is closed or the
     code doesn't exist.
   - GET /api/attendance/sessions/course/:courseId (roles: lecturer,
     admin) — list all sessions for a course with counts of present vs
     absent.
   - GET /api/attendance/my-history (role: student) — list the logged-in
     student's attendance records across all courses, optionally filtered
     by course via query param.

Mount the route file in server.js under /api/attendance.

--------------------------------------------------------------------------------
Build the reporting module, protected by authMiddleware:

1. controllers/reportController.js + routes/reportRoutes.js:

     Return a summary of how many alert emails were sent.

STEP 16 — PUSH TO GITHUB & DEPLOY TO RENDER (two services)
================================================================================
WHAT IT DOES: Gets your code onto GitHub and deploys the backend and
frontend as two separate Render services, connected to MongoDB Atlas and
Brevo — this is also how you'll run the app for the first time.

DO THIS YOURSELF (all in the browser, no installs):
1. In the GitHub web editor or Codespaces, commit all files via the
   Source Control panel and push to your GitHub repository.
2. Deploy the backend:
   - Render → New → Web Service → connect your repo.
   - Set "Root Directory" to `server`.
   - Build Command: npm install
   - Start Command: npm start
   - Add Environment Variables: MONGO_URI, JWT_SECRET, BREVO_API_KEY,
     BREVO_SENDER_EMAIL, CLIENT_URL (fill CLIENT_URL in after step 3,
     once you know the frontend's URL).
   - Deploy, and note the resulting URL (e.g.
     https://attendance-api.onrender.com).
3. Deploy the frontend:
   - Render → New → Static Site → connect the same repo.
   - Set "Root Directory" to `client`.
   - Build Command: npm install && npm run build
   - Publish Directory: dist
   - Add Environment Variable: VITE_API_URL set to the backend URL from
     step 2 (e.g. https://attendance-api.onrender.com/api).
   - Deploy, and note the resulting URL (e.g.
     https://attendance-system.onrender.com).
4. Go back to the backend service's Environment tab and set CLIENT_URL to
   the frontend URL from step 3, then trigger a manual redeploy so CORS
   picks it up correctly.
5. Open the frontend URL to confirm the login/register pages load and can
   reach the API.

Every push to GitHub afterward triggers Render to automatically rebuild
and redeploy both services.
